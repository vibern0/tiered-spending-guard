# Installable Safe 4337 contract routing: focused design proposal

**Date:** 2026-11-19
**Status:** Safe 1.5 and reviewed-function scope selected by the user on 2026-11-20. Local implementation and tests authorized; no network deployment or adoption into the active vault profile.
**Request:** Let an existing ERC-4337 account install enforcement so selected contract interactions can execute only through the account's 4337 route.

## Feasibility boundary

ERC-4337 defines account validation and EntryPoint execution, not a universal mandatory transaction hook or module installer. A separate contract cannot intercept every execution path of an arbitrary account merely by being installed. This repository can enforce this property for a **Safe 1.5 account** with both Safe transaction and module guard slots under one fail-closed policy. Older Safes without module guards, non-Safe 4337 accounts, and Safes with unremovable conflicting execution authority cannot satisfy the same installation guarantee. [ERC-4337 account interface](https://eips.ethereum.org/EIPS/eip-4337#smart-contract-account-interface), [Safe module guards](https://docs.safe.global/reference-smart-account/guards/setModuleGuard).

The requested destination list is an **execution-route rule**, not a fallback rule. Safe fallback receives calls *to* the Safe, such as `validateUserOp` and `isValidSignature`. Outgoing owner and module executions enter distinct guard hooks. The rule must reject a direct owner call to a listed target, admit only an exact approved 4337 path to it, and deny every other module. A listed call cannot become an arbitrary-call exception to the existing X/Y/Z spending policy: the first vault profile accepts only native transfers and selected ERC-20 `transfer` calls. New contract functions require a separate decoded policy with bounded effects. [Fallback manager](https://github.com/safe-fndn/safe-smart-account/blob/dc437e8fba8b4805d76bcbd1c668c9fd3d1e83be/contracts/base/FallbackManager.sol), [current guard](../../../contracts/TieredSpendingGuard.sol).

| Approach | What it needs | Result |

| **A. Safe 1.5 route profile with a restricted fallback and guard** | A reviewed fallback that handles only the required EntryPoint selectors, a guard in both slots, exact module/handler/EntryPoint pins, and one guarded installation/maintenance process. | **Selected for local implementation.** Can preserve the no-arbitrary-message rule and make listed, decoded actions 4337-only. | **B. Standard Safe4337Module as fallback plus a route-aware guard** | New nested-call guard phase and exact module identity. | Can route listed actions but still accepts arbitrary Safe ERC-1271 messages outside both guards. The [local probe](../../evidence/2026-11-19-standard-safe4337-probe.json) demonstrates this. It does not preserve the current threat model. |
| **C. One module installable on any ERC-4337 account** | A mandatory interception hook common to all existing account implementations. | Not supported by ERC-4337. Implementations using another modular standard would need separate adapters and installation proofs; the universal claim is unavailable. |

The stock module cannot simply sit behind Safe 1.5's `ExtensibleFallbackHandler`: its method router invokes `IFallbackMethod.handle(...)`, which the stock module does not implement, and its built-in ERC-1271 function falls back to Safe owner signatures. A direct forwarding call to `Safe4337Module.validateUserOp` also changes `msg.sender`, which the module checks against the Safe. Building an adapter is therefore a custom handler/security composition, not a configuration-only change. [Extensible method routing](https://github.com/safe-fndn/safe-smart-account/blob/dc437e8fba8b4805d76bcbd1c668c9fd3d1e83be/contracts/handler/extensible/FallbackHandler.sol), [standard module caller check](https://github.com/safe-fndn/safe-modules/blob/75e56fd52b0ddbe01dc237eaae7edb9a102ffc5c/modules/4337/contracts/Safe4337Module.sol#L133).

## Proposed Safe-specific contract and installation behavior

This section specifies the selected local research behavior. It does not authorize network deployment.

- Scope the first profile to one verified Safe 1.5 and its configured EntryPoint, passkey signer, Delay, guard, and handler. Reject unknown Safe versions, owners, enabled modules, fallback, guard slots, pre-existing token allowances, or incompatible policy state. “Existing” means an eligible existing Safe, not any arbitrary deployed account.
- Install/activate both guard slots and the restricted fallback as one reviewed atomic Safe action. No intermediate state may allow the new AA route with only one guard slot. The already enabled account path must remain usable during transition; a failed installation must leave the old state intact. No user/app EOA or backend signing key is added.
- Store a bounded target-and-selector policy onchain. Each entry identifies an exact target, function selector/canonical calldata shape, operation, native value bound, and any asset effect that X/Y/Z must count. Unlisted calls retain the current fail-closed policy. Adding or widening an entry is delayed maintenance; removing or tightening one may be immediate only if the guard proves monotonic restriction.
- In the owner guard, reject a listed action unless the authenticated AA envelope phase is active and commits to the exact Safe transaction hash, nonce, target, value, calldata, operation, and signer set. In the module guard, admit only the pinned AA module/handler's exact approved envelope, with one matched inner owner action and ordered successful after-hooks. Deny direct module-to-target calls, other modules, delegatecalls, batches, approvals, Permit/Permit2, arbitrary messages, and fallback-spoofed guard hooks.
- Keep existing X/Y/Z accounting and Delay queue/ready execution separate from routing. A listed interaction whose effects cannot be bounded by a reviewed decoder is unsupported. The fallback rejects both ERC-1271 selectors and unknown selectors onchain. For listed targets, ready Delay execution must traverse the restricted 4337 router; direct public Delay execution is rejected. Handler, route-policy weakening, module, and fallback replacement require delayed enumerated maintenance actions before this profile can be adopted.

## Local rejection-first tests

Use a real Safe 1.5 proxy, real passkey contract signatures, published 4337 and Delay artifacts, and an actual local EntryPoint/bundler-compatible path where applicable. The existing probe covers ABI compatibility only and is not these tests.

1. **Install topology:** atomic setup succeeds only from a compatible Safe; mutation of either guard slot, fallback, module set, EntryPoint, owner, runtime hash, or existing allowance fails verification. Failed setup rolls back. An already enabled unrelated module cannot remain as an unguarded route.
2. **Destination route:** a normal owner transaction to a listed target fails; the same exact authorized action through the 4337 route succeeds; changed target, selector, calldata, value, operation, nonce, or signer fails. A direct AA module transfer to the target fails unless it traverses the approved inner policy path.
3. **Spending and Delay:** native/ERC-20 X/Y counters and ERC-20 balance proof are unchanged by routing; over-Y execution queues, waits Z, can be cancelled/expire, and executes only from the verified Delay path. Failure consumes no allowance.
4. **Fallback and other bypasses:** both ERC-1271 selectors, approved hashes, spoofed caller suffixes, forged guard hooks, alternate modules, delegatecalls, batches, approvals, and immediate route-policy weakening fail. Replacing/removing either guard or fallback requires delayed maintenance.
5. **Provider and liveness:** prove the exact account/EntryPoint version, strict validation trace, sponsored zero-prefund path, UserOperation receipt success, and restart/retry nonce behavior locally before any network test. A failed sponsor makes the operation unavailable without charging vault funds.

## Decision and current gate

The user chose existing Safe 4337 accounts and reviewed functions only on 2026-11-20. The repository's [2026-10-19 native amendment](../../../../../AGENTS.md) currently excludes enabled AA modules and generic messages and permits only its named restricted handler/bootstrap. The [native plan](../plans/2026-10-19-native-safe-4337.md) also leaves the ordinary-Safe live gate open. This proposal records the discrepancy explicitly. Local research implementation may proceed under the user's newer instruction, but this does not alter the active plan, deploy anything, or claim a generic installable ERC-4337 module exists.

**Local implementation status (2026-11-20):** The experiment uses a separate `TieredSpendingGuard4337` variant so the original guard and its pinned maintenance hash do not change. The listed selector set is currently hard-coded to the existing reviewed native and ERC-20 transfer shapes; there is no general selector registry. A local EntryPoint 0.7 `handleOps` transfer, direct-route rejection, AA delayed queue/ready execution, cancellation, expiry, fallback rejection, and atomic install/rollback tests pass. The existing maintenance helper cannot replace the variant, and the topology verifier cannot prove absent historical token allowances or enumerate the local Delay fixture's upstream modules. Sponsorship, browser passkeys, live runtime anchors, alerting, and profile repair remain unproved. **Do not install this profile on a funded Safe.**
